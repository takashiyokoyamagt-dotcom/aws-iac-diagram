## 0. 基本の考え方

1. **基準は、スクリプトで機械的に測れる「自動の基準」を中心にする。** どの環境（Claude Code、VS Code + Copilot、gh-aw）でも同じ判定になるように（PLAN 1.3 の 9）。機械では判定できないものは「半自動の基準」とし、次の2つを守る。
   - 判定するのは、生成したエージェントとは別のサブエージェント（または人）
   - 判定の根拠（規則表のどの行か、入力のどの行か）を記録に残す

   半自動の基準は、1.3 の抜き取りと点検表、1.4 の許す違いの一覧づくり、5章の目視の採点の3つだけ。
2. **割合の基準と、1件でもあれば不合格の「重大な誤り」（1.5）を分ける。** 割合が高くても、構成図を見て誤った判断をさせる誤りは許さない。
3. **全体の値だけでなく、入力ごとの下限も設ける。** 大きい入力の数字に、小さい入力の失敗が埋もれないように。
4. **結果を見てから基準を緩めない。** 基準を満たせないときは、直すか、「既知の制約」として README に書くかを、ユーザーに確かめて決める。正解 IR・点検表・期待する差分は、ツールの出力を見る前にファイルとして確定させる。
5. **ラベルと名前はスクリプトが決める。** B3 の規則（Name タグ → 名前属性 → 論理名、省略規則）で決める。エージェントが変えてよいのは、説明の `.md` の文章と、ユーザーへの確認の質問だけ。だから IR（canonical 部）はエージェントによらず決まる。

## 1. 図の正しさ（IR の比較）

### 1.0 比べ方

- 単位は ir-schema.md の 5 のとおり: N = ノード `(id, type)`、E = 辺 `(from, to, kind)`（向きを区別）、P = 入れ子、C = 網羅分類、付随 = 確信度・ラベル。canonical 部は `note` を除く `nodes` と `edges`。
- **比べる前に、ノードの id を対応づける。** 出力 O と正解 G のノードを、由来部（`sources.*.resources`）の address で突き合わせ、O の id を G の id に置き換えてから N・E・P を比べる。名前を1つ間違えただけで、N・そのノードの辺・P が同時に外れるのを防ぐため。名前の誤りは、別の指標「名前の一致率」で数える。（ir-schema.md の 5 と同じ）
  - 対応づけに使うのは、網羅分類が `drawn` のリソースの address だけ（`merged_into`・`hidden` は使わない）。1つのノードに `drawn` の address が複数あるときは、どれか1つでも一致すれば対応づける。
  - address で対応づけられないノード（合成ノードなど）は、id のまま比べる。
  - **名前の一致率** = address で対応づけたノードの組のうち、O のもとの id と G の id が一致する組の割合。
- 複数の入力をまとめた値は、件数を合算してから割る（マイクロ平均）。
- **入力ごとの下限の使い方:** 母数（|G|、適合率なら |O|）が 10 以上のときは割合の下限を使う。10 未満のときは「誤り 1 件以内」にする。辺が 3 本しかない入力では、1本の誤りで割合が 0.67 になってしまうため。
- 対（TF 版と SAM 版など）は、別々の入力として数える。名前が違うので、正解 IR も別々に書く。

### 1.6 CloudFormation の検算（C1）。アダプタの参照の取りこぼし（フェーズ1）

2026-10-17 にユーザーの了承を得て変更した（もとは「cfn-lint のグラフの辺が、正規化した図の辺の根拠か、非表示・統合の規則で説明できる」だった。正規化ができる前のフェーズ1 では測れず、正解 IR の根拠の書き方とも合わなかったため）。

主セットと補助セットの CFN と、自作の fixture の CFN のすべてについて、`cfn-lint --build-graph` のグラフの辺を1本ずつ、アダプタの出力（raw IR の `references`。ir-schema.md の 7.3）と照合する（cfn-lint は 1.57.2 に固定。`pyproject.toml` と同じ）。

- **基準:** cfn-lint の辺 (A, B, 属性の場所) のすべてに、対応する参照 (from, to, path) が raw IR にあること。**対応の無い辺が 0 件**（フェーズ1 の完了基準）。
- **対応づけのしかた**（スクリプトで行う）:
  - cfn-lint のグラフは、`cfn-lint --build-graph` と同じく変換（SAM の Globals、Fn::ForEach）の後のものを使う。照合は `aws-iac-diagram-workspace/tools/c1_check.py` で行う（引数を省くと、この節の対象をすべて探し、1つでも欠ければ失敗にする）。
  - cfn-lint の辺の両端を、raw IR の address に直す。ネストスタックの子テンプレートの論理ID には `<親の論理ID>/` を付ける。複数のスタックでは `<スタック名>::` を付ける。親のテンプレートの辺（スタック → スタック）は、raw IR の参照の `through` の先頭（`NetworkStack.Outputs.…`）と照合する。
  - cfn-lint の属性の場所を、**最初の `Ref`／`Fn::*` の位置で止めて**から、raw IR の `path` と比べる。**(from, to) が一致し、片方の場所が、要素の区切り（`.` と `[n]`）でもう片方の前の部分になっていれば対応とする**（前方一致。cfn-lint は `Fn::Sub` などの位置で止まり、raw IR は `$json` の中の位置まで続けるため。2026-10-17 にユーザーの了承を得て、完全一致から前方一致に変えた。同日、フェーズ1 の終わりのレビューを受けて、ユーザーの了承を得て「`Fn::*` の要素を除いてから比べる」を「最初の `Ref`／`Fn::*` の位置で止める」に直した。除く方式では `Fn::If` の中の要素の位置（`Tags[1][0]`）が raw IR の選んだ側の位置（`Tags[0]`）とずれて、正しい参照でも外れるため）。`AWS::NoValue` で消えたリストの要素の位置のずれも、止める方式なら前方一致で吸収できる（ir-schema.md の 7.3）。
  - `fn`（Ref／GetAtt／Sub）は照合に使わない（cfn-lint は Sub の中の参照を Ref／GetAtt として数えるため）。
  - cfn-lint は条件を評価しないので、`state` が `pruned`／`unevaluated` の参照も照合に使う。`enabled: false` のリソースの参照も同じ。
- 逆向き（raw IR にあって cfn-lint に無い参照）は、件数と内訳を参考値として出す（基準にはしない）。

### 1.7 変異テスト（C4）

入力に機械的な変更を加え、IR がそれに追従するかを確かめる。変更はスクリプトが作る（操作の定義と乱数の種を記録する）。変更の種類は次の6つ: リソースの追加、リソースの削除、参照の付け替え、条件（count・Conditions）の切り替え、名前の変更、SG のルールの追加・削除。

| 対象 | 期待のしかた | 基準 |
|---|---|---|
| 自作の fixture（各構成で 6 種類 × 1 回以上、計 30 以上） | 期待する差分を、IR のパッチ（追加・削除するノードと辺の id、変わる属性）の JSON で先に書く。実際の差分と完全に一致するか | **100%** |
| 主セット（各入力で、適用できる種類のうち 3 種類以上） | 変更の種類ごとに決めた性質を満たすか（下の表） | **100%**（適用できない変更は除く。例: SG が無いサーバーレスでは SG のルールの変更を除く） |

**共通の性質（局所性）:** IR の差分（ノード・辺・入れ子・網羅分類）は、変更したリソースの address が、変更の前か後の `sources`（網羅分類の address、または辺と入れ子の根拠）に出てくるものだけに限られる。ほかの差分は 0。

変更をかける対象は、スクリプトが次の条件で選ぶ（条件に合う対象が無い入力では、その種類を「適用できない」とする）。

| 変更の種類 | 対象の条件 | 共通の性質に加えて満たすべきこと |
|---|---|---|
| リソースの削除 | 描くリソースで、ほかのリソースから参照されず、枠（VPC・サブネットなど）でも合成ノード（AZ・`external/internet`）の根拠でもないもの | そのノードが消える |
| 関係リソースの削除（listener、permission など） | R-* で辺に変換されるもの | 対応する辺が消える（ほかに根拠があれば残る） |
| 名前の変更 | 変更後の名前が、ほかのノードの名前と重ならないもの | id の key と `name`・`label` 以外の差分が 0 |
| 条件の切り替え（count を 0 にするなど） | 単純な式（`var.X ? 1 : 0` など）の count／Conditions | 対象が H-COND-FALSE になる。合成ノード（AZ など）と入れ子の差分は、共通の性質の範囲で許す |
| リソースの追加 | 参照も、IAM・環境変数の文字列の一致も生まないことが分かっている型（例: 単独の SNS トピック） | ノードが1つ増える。推定の辺は増えても誤りにしない |
| 参照の付け替え | 辺を作る参照だけ（`subnet_id` など配置を決める属性は除く） | 辺の端が付け替わる。ノードと入れ子の差分は 0 |
| SG のルールの追加・削除 | 既存の SG の ingress | R-SG の辺が1本増える／減るか、既存の辺のラベルが変わるだけ。`external/internet` の辺の増減は、CIDR が外部のときだけ許す |

## 2. 見やすさ（.drawio の検査）

validate.py で、Python だけで測る（フェーズ4 の完了基準）。draw.io は辺の経路を決めるので（失敗知見 5。`orthogonalEdgeStyle` で waypoint を置かない）、`.drawio` には経路そのものが無い。そこで、次の**近似のモデル**で判定する。

### 2.1 測り方の定義

- 座標はすべて絶対座標（親からの相対座標を足し合わせたもの）で扱う。
- **重なり:** 2つのノード（アイコンか枠）の矩形の交差の面積が 0 より大きいこと。接しているだけなら許す。親子（枠とその中身）は対象外。兄弟の枠どうしは対象。
- **はみ出し:** 子の矩形が、親の枠の矩形の外に出ること。
- **辺の端点:** 端がアイコンのノードなら、その中心。端が枠（サブネットなど）なら、相手のノードに最も近い枠の辺の中点。
- **辺の経路のモデル:** 2つの端点を、次の4通りで結ぶ。
  - L 字の2通り（横 → 縦、縦 → 横）
  - Z 字の2通り（中点で折れる。横 → 縦 → 横、縦 → 横 → 縦）

  draw.io の `orthogonalEdgeStyle` はこのどれかに近い経路を作る。
- **貫通:** 辺の経路が、次のどれでもないノード・枠の矩形と交わること。
  - 両端のノード
  - 両端の祖先の枠（その境界を越えるのは許す）
  - 端が枠のときは、その枠の子孫

  **4通りの経路のすべてが貫通するときだけ**誤りにする（draw.io がどれかを選べるため）。
- **ラベルの矩形:**
  - 大きさ: 幅 = 文字数 × フォントの大きさ × 係数（全角 1.0、半角 0.6）、高さ = 行数 × フォントの大きさ × 1.2 で近似する。
  - ノードのラベルの位置: アイコンの真下の中央（`verticalLabelPosition=bottom`）。
  - 辺のラベルの位置: 経路の中点。4通りの経路のそれぞれで置き、**すべてで重なるときだけ**誤りにする。
- 近似が実際の描画と合っているかは、draw.io がある環境（CI の render-png）で SVG に書き出して実際の経路で数え直し、**参考値**として出す（合否には使わない）。

## 3. 安定性（C5、3回実行）

| 指標 | 基準 |
|---|---|
| 同じ入力を同じ環境で2回実行したときの IR・`.drawio`・`.mmd`・`coverage.md` | **バイト単位で一致**（すべての入力） |
| Windows と Ubuntu の IR・`.drawio`・`.mmd`・`coverage.md` | **バイト単位で一致**（CI で確かめる） |
| PNG | CI の固定した環境（draw.io の版・ランナーのイメージ・フォント）で2回実行して **バイト単位で一致**。5a で一致しないと分かれば、ユーザーの了承を得て「画素の差 0.1% 以下」に置き換える。画素の差 = 画像の大きさが同じで、どれかの色のチャンネルが違う画素の数 ÷ 全画素数 |
| SKILL 全体（エージェントを含む）を同じ依頼で3回実行したとき | IR の canonical 部が **3回とも一致**。説明の `.md` の「推定した辺の一覧」が、辺の id で照合して **3回とも漏れが無い** |

- 3回実行は、コストを抑えるため「自作の fixture 5構成（TF 版だけ）＋主セットから 4 入力（T07、T09、T16、C02）」で行う。
- 確認の質問への答えは固定する（台本の回答を使うか、`--env` などの引数で先に指定する）。答えの違いで IR が変わるのを、誤りと区別できるように。
- 「推定した辺の一覧」は、スクリプトが `sources` から作る。エージェントはそれを説明の `.md` に載せるだけにする。

## 5. 目視の採点（C6）。半自動の基準。Claude Code でだけ行う

生成したエージェントとは別のサブエージェントが、PNG を見て観点表で採点する。Copilot と gh-aw では行わない（PLAN 1.3 の 9）。

| 観点 | 見ること |
|---|---|
| 正しさ | 入力の説明（README）と図が食い違っていないか |
| 読みやすさ | 主な流れ（利用者 → 入口 → 処理 → データ）を目で追えるか |
| 配置 | 枠（VPC・AZ・サブネット）の入れ子と並びが自然か |
| ラベル | 名前とラベルが読めて、意味が通るか |
| 凡例と説明 | 推定の辺の凡例があり、説明の `.md` と図が合っているか |

- 点の目安: **1** = 誤った判断を招く、**2** = 大きな直しが要る、**3** = 読めるが直しが要る、**4** = 小さな直しで使える、**5** = そのまま使える。
- 合格は、平均 **4.0 以上**で、**2 点以下の観点が無い**こと。
- 対象は、自作の fixture 5構成（TF 版）と、主セットの 12 入力と、大きいサンプル（T17、T19、C05）。大きい図はビューごとに採点する。
- C6 は合否の補助として扱う。自動の基準を満たし、C6 だけが不合格のときは、指摘をユーザーに見せて直すかどうかを決める。
