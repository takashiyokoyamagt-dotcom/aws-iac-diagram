## 8. 決めなかったこと（後のフェーズで決める）

- **複数ビュー（B2）の詳細度:** IR には持たせない。どのノードをどのビューに出すかは、型ごとに規則表の型の行（`data/rules/types/`）の列で決める（フェーズ4。IR を表示の都合で変えないため）。
- **TF のリソースの属性の値を、設定に書いた値から決めるか**（`cidrsubnet(aws_vpc.main.cidr_block, 8, 1)` など。いまは `$res` のまま、関数の引数なら `$unknown`）。図の `cidr` に要るかを、フェーズ3 の正規化で確かめてから決める。
- **TF の `.tf.json` を .tf だけで読むか:** 読まないと決めた（フェーズ2 の手順5。7.2 の「TF のそのほかのブロック」）。HCL の JSON の書き方では、`"ingress": {…}` が入れ子のブロックか、オブジェクトの値の属性かが書き方から決まらず、決めるには provider のスキーマが要る（props の形が .tf と plan JSON で変わる）。公開サンプルに無く、plan JSON と一緒なら正しく読める（plan の `configuration` はスキーマで読んだ後の形）ので、.tf だけのときは警告（`TF-TFJSON-UNSUPPORTED`）に留める。provider のスキーマ（`terraform providers schema -json`）を入力に取るようになれば読める。
- **診断の `code` の一覧:** CFN と TF は 7.5、正規化の `NORM-…` は 10 章のとおり（正規化のものは、辺の段階を作るときに足す）。
- **統合先が見つからない M-\*:** 規則表に「統合先が無いときの H-\*」の規則（設計草案 4.1 の案。ID はまだ決めていない）が無い（規則表は凍結しているので足していない）。フェーズ3 の手順 3a では、統合先が見つからない M-\* は仮の分類（`merged_into`、`into` が空。`validate_ir.py` は通らない）のまま残し、`NORM-MERGE-TARGET`（warn）を出す。規則を足すかは、主セットで件数を見てから決める（2026-11-07 の時点で、自作 10 入力と主セット 12 入力では 0 件）。
- **辺ができず fallback の無い R-\*（フェーズ3 の手順 4a）:** R-LB-LISTENER・R-LB-TG・R-APIGW-*・R-LAMBDA-ESM・R-SNS-SUBSCRIPTION・R-S3-NOTIFICATION・R-BEDROCK-DATA-SOURCE・R-EVENTS-TARGET・R-GLUE-TRIGGER には、辺ができなかったときの非表示の規則（`fallback`）が無い。規則表は凍結しているので足さず、分類を仮（`merged_into`、`into` が空）のまま残して `NORM-RELATION-NOEDGE`（warn）を出す（`normalize_ir.py` は終了コード 1）。主セットでは、T12 の条件の無い Glue のトリガー（規則の文のとおり辺を作らない）が当たる（T11 の Step Functions を統合先にする REST API は、`uri` がアクションの文字列でも `request_templates` の中のステートマシンへの参照から辺を作る。T11s の API は OpenAPI の定義（`AWS::Include`）の中にあり raw に載らないので、辺の根拠が無い既知の制約のまま）。規則を足すか（例: 条件の無いトリガーの H-*）は、規則表の凍結を解くときに決める。
- **IPv6 の既定のルート（フェーズ3 の手順 4a）:** サブネットの `attrs.access` は、規則表（placement.toml の `[[attr]]`）の文のとおり `0.0.0.0/0` → インターネットゲートウェイのルートだけで `public` にする。`::/0` → インターネットゲートウェイ（や Egress-only のゲートウェイ）のルートは辺（R-ROUTE、ラベル `::/0`）にはなるが、`access` は `private` のまま（IPv6 だけで公開するサブネットは private に見える制約）。変えるなら規則表の文を直す。
- **黒箱のモジュールの入力からの推定の辺（フェーズ3 の手順 4b）:** 2 章の「モジュールの入力に渡したノード: モジュール → そのノードの辺」は、規則表に規則 ID が無い（`sources.*.edges[].rules` に書く ID が決まっていない）ので、まだ作らない（入力の参照は E-NOEDGE-FROM-RULE ではなく、参照する側が描くノードなので会計では `NORM-UNUSED-REF` か E-NOEDGE-* になる）。モジュールの出力への参照（参照した側 → モジュール）は、2 章のとおり E-ENV-REF に当たるときだけ `inferred`・`request` で作る。規則 ID を足すかは、規則表の凍結を解くときに決める。
- **コードに置いた表（規則表の凍結を解くときに edges.toml へ移す）:** SAM のポリシーテンプレート → 代表のアクションの表（`scripts/aws_iac_diagram/normalize/iam.py` の `TEMPLATE_ACTIONS`。E-IAM の kind を決める）と、上の黒箱のモジュールの入力からの推定の辺の規則。どちらも規則表に置くべきデータだが、規則表を凍結しているので、手順 4b ではコードに置いた（前者）・作らない（後者）。
- **インターネットへの公開の範囲（フェーズ3 の手順 5）:** R-SG の `0.0.0.0/0`／`::/0` からの辺は、規則表の文のとおりインターネット向けの LB とパブリック IP の EC2 だけに作る。internet → LB に使うのは、TCP のポートの範囲が決まるルール（と全プロトコル）のうち、出したリスナーのポートを許すものだけ（UDP・ICMP・値の決まらないルールは当たらない。ポートの決まらないリスナーは全ポートのルールにだけ当たる）。EC2 は `associate_public_ip_address` が書かれていれば、その値が真のときだけ公開（偽・決まらない値ならパブリックサブネットでも公開としない）。`publicly_accessible = true` の RDS（T03）、パブリック IP を持つ ECS タスク（`assign_public_ip`）、NLB の SG なしの公開などは辺にしない（規則表の凍結を解くときに決める）。
- **SG を付ける属性の範囲（フェーズ3 の手順 5）:** 「SG を付けたリソース」は refs.toml の E-NOEDGE-SG の属性（`security_groups`・`security_group_ids`・`vpc_security_group_ids`・`VPCSecurityGroups`）の参照だけで決める。CFN の EC2 の `NetworkInterfaces[].GroupSet` と起動テンプレートの `LaunchTemplateData.NetworkInterfaces[].Groups` は表に無いので、そこで付けた SG からは辺ができない（規則表の凍結を解くときに属性を足す候補）。
- **WebSocket の API（フェーズ3 の手順 5）:** `protocol_type`／`ProtocolType` が `WEBSOCKET` の API Gateway は描く型（`apigw_http_api` の `when` は HTTP だけ）にも internet → API の辺（N-EXT-INTERNET。ラベル `HTTPS`）にもしない。描くか、入口の辺のラベル（`WSS` など）をどうするかは規則表の凍結を解くときに決める。
- **R-SG の組合せの数（フェーズ3 の手順 5）:** 上限は設けていない（設計草案 8 章の 6）。主セットでは R-SG の辺は 0 本（T03 は上の公開の範囲、T16 はクラスタとノードの SG が同じクラスタのノードに付くので自己ループ）。T19・T20 の辺の数は手順 6 で測る。
- **E-ENV-STR の文字列の一致（フェーズ3 の手順 4b）:** 環境変数の文字列が 2 つ以上のリソースの名前に当たるとき（同じ名前の API とユーザープールなど。C02）は、どれを指すか決まらないので辺にしない。
- **M-\* の統合先の手がかりとしての DependsOn:** 参照（DependsOn 以外）と名前の一致で決まらないときの最後の手としてだけ使い、統合される側が自分で宣言した DependsOn（外向き）で、候補がちょうど 1 つのときに限る（`NORM-MERGE-DEPENDS-ON`、info）。ほかのリソースから統合される側への DependsOn は使わない（関係の無いリソースが順序のためだけに DependsOn を書くことがあるため）。TF の `opensearch_index` は provider の `url` でしかコレクションを指さず、raw IR には DependsOn しか残らない。
- **AZ のノードの限界（フェーズ3 の手順 3b）:** サブネットが AZ を `availability_zone_id`（`AvailabilityZoneId`。`apne1-az1` など）だけで指すときは、AZ 名に読み替えず AZ のノードを作らない（`NORM-AZ-UNKNOWN`。サブネットは VPC の下）。AZ 名の key は小文字にして作るので、大文字と小文字だけが違う AZ 名は 1 つの AZ のノードにまとまる（name・label は最初に作ったサブネットのもの）。
- **ノード ID の重なり**（2章）を解いたときの、TF／CFN の対応表の形（フェーズ3 の正規化で決める。フェーズ2 では、TF／SAM の対の raw IR のリソースの型の多重集合を `tf_public_check.py` で比べるところまで行った。違いはすべて理由つきの表に残っている）。
